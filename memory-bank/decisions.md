| 2026-09-02 | **Deploy on-premise: one Docker host inside the clinic LAN running self-hosted Supabase + Next.js, with the portals reached through an outbound-only tunnel** | The 2026-09-02 onsite visit found the clinic running Microsoft Access against SQL Server on a wired in-house LAN with no internet dependency at all. A cloud deployment would make an internet outage stop Reception from admitting patients — an unacceptable regression for a clinic that today has no such dependency. On-premise inverts the failure mode correctly: an outage makes the portals temporarily unreachable while the clinic keeps working at full LAN speed. It also moves compute off the old workstations (today the Access front-end runs on each PC, which is why staff call it slow) and produces the System Installer + Installation Guide the capstone requires as final deliverables. Self-hosted Supabase rather than plain Postgres because the app is coupled to Supabase Auth, Storage, Realtime and `auth.uid()` RLS — not merely to Postgres — across 9 importing files; swapping the platform means rewriting auth and authorization from scratch. Pointing the app at the clinic's own SQL Server is rejected outright: it would mean that rewrite *plus* adding a case lifecycle, DPA gating and audit logging to the live production database the whole clinic depends on and nobody on site can administer. Accepted costs: backups, uptime, TLS renewal and patching become ours. The 2026-08-27 Singapore project becomes staging — and that work's migration-history repair is what makes a fresh self-hosted instance reproducible (48/48 from empty). TLS termination for the tunnel is deliberately **not** decided here; it belongs to AHI's DPO under RA 10173. | Decided — not yet implemented; see `docs/superpowers/specs/2026-09-02-clinic-architecture-adaptation-design.md` §4 |
